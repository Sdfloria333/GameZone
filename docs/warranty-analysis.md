# Requirement 4 - Warranty Module: Analysis

## 1. Class hierarchy for the two warranty types

The common attributes (associated product, start date, end date) belong in an abstract `Warranty` class, the same way `Product` already centralizes `id`, `title`, `price`, and `stockQuantity` for `Console` and `Videogame`. What differs — duration, coverage description, and cost — is expressed as abstract methods that `BasicWarranty` and `ExtendedWarranty` override, mirroring how `Console` and `Videogame` each override `Product.getDescription()`. The OOP mechanism that avoids duplicating code is method overriding (runtime polymorphism): any code holding a `Warranty` reference calls `getDurationInMonths()`, `getCoverage()`, or `getAdditionalCost(Product)` without needing to know which concrete subclass it actually has.

## 2. Location of the "consoles only" rule

This decision does not belong in `Product`, `Console`, or `Warranty` — none of those classes should need to know that warranties exist. It belongs in the service layer, in `SaleService.registerSale()`, at the same point where `Sale` details are already built and where promotion logic is already applied through `promotionService`. The mechanism used to verify the real type of a `Product` is `instanceof`, exactly as `ProductService` already does in `reduceStock()` and `restoreStock()` (`product instanceof Console`), so `SaleService` would use the same check — `if (product instanceof Console)` — to decide whether to auto-generate a `BasicWarranty`.

## 3. Where the expiration date is calculated

The expiration date should be calculated in the constructor, following the same pattern already used by `Return`: its "creation" constructor calls `calculateRefundAmount()` automatically so the object is valid as soon as it exists, while a second, "reconstruction" constructor accepts an already-known value and is used only when loading from persistence. `Warranty` would follow the same two-constructor design: the creation constructor receives the duration from the subclass via `super(productId, startDate, durationMonths)` and computes `endDate = startDate.plusMonths(durationMonths)` right there, while the reconstruction constructor used by `WarrantyRepository.loadAll()` receives the already-persisted `endDate` directly — avoiding recalculation, and avoiding the risk of a base constructor calling an overridable method before the subclass is fully initialized.

## 4. Applying the extended warranty cost during sale registration

The extra cost must be added inside `SaleService.registerSale()`, in the same block where the total is currently set — steps 5 and 6 of the existing method, right where the subtotal is combined with (or without) the promotion discount. Concretely, `registerSale` needs: (a) a way to know, per `SaleDetail`, whether an extended warranty was selected, since neither `SaleDetail` nor `Console` currently carries that information; (b) for each applicable product, an instantiated `BasicWarranty` or `ExtendedWarranty`, whose `getAdditionalCost(product)` is summed into a `totalWarrantyCost`; and (c) that `totalWarrantyCost` added into both branches of the existing total calculation (`newSale.setTotal(newSale.getSubtotal() + totalWarrantyCost - discount)`, and the equivalent no-promotion branch), plus a new `WarrantyService` dependency injected into `SaleService` — the same way `accessoryService` and `promotionService` already are — so the created warranties can be persisted through `WarrantyRepository.saveAll()`.

## 5. Location of the "expiring soon" query

This method belongs in `WarrantyService`, as the direct counterpart to `ReturnService.generateMonthlyBalance()`: it needs to load all persisted warranties (`WarrantyRepository.loadAll()`) and filter them against `LocalDate.now()` plus a 30-day window, which is exactly the kind of date-based business logic that `ReturnService` already keeps out of its repository. Its only dependency is `WarrantyRepository`, since the check depends purely on each warranty's own `endDate`. This placement is coherent with the layered architecture for the same reason `generateMonthlyBalance` lives in `ReturnService` and not `ReturnRepository`: repositories in this project are limited to reading and writing raw JSON records, while any logic that interprets that data against a business rule belongs to the service layer.
